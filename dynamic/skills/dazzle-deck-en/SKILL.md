# dazzle-deck-en: single-HTML dazzling presentation deck

What you deliver is not a "slideshow" but a **dynamic visual performance** staged in the browser: a continuously running animated background, per-page entrance choreography, inter-page transition effects, keyboard interactivity — all while keeping rigorous typography, authentic content, and zero console errors.

## 0. Iron rule for reading references (must be obeyed before starting, highest priority)

This skill's SKILL.md and `references/` (`style-families.md`, `fancy-cookbook.md`) are **both longer than a single read_file output limit and will be truncated at a line boundary**. When truncated, the end of the result always carries a hint line of the form:

```
[… 截断：已显示第 A–B 行（共 N 行）；续读 offset=M]
```

**Iron rule: the moment you see this hint line, you must immediately read_file the same file again with the `offset=M` it provides; loop like this until a read no longer carries the truncation hint — at that moment, and only at that moment, have you read to the end of the file.**

- **Trust the signal only, never count reads**: the criterion is always "does this read still carry the truncation hint", never "how many times have I read". It may take one, three, or five reads; the count changes whenever the file changes; the only invariant is "no truncation hint = reached the end". **Never stop based on a read count.**
- **No moving forward before reading it all**: before a reference has been read until "no longer truncated", you are forbidden to enter the next phase, and forbidden to write_file / edit any deck file (not plan.md, not deck.html).

**Red Flags — for reference reading, if any of these occurs, stop and go back to continue reading:**

- The result ends with `续读 offset=` but you did not continue → violation; immediately continue reading with that offset.
- The thought pops up "the opening covers what I need / the rest must be details / start now and backfill later" → this is exactly the excuse that produces mediocre decks; it does not hold.

## 1. Deliverables and boundaries

- Final deliverable: `**deck.html**` at the workspace root (plus `assets/` if generated images are used, with images referenced by the relative path `assets/img_NN.png`; without generated images, deck.html is the only deliverable).
- Canvas **1280×720 (16:9)**, a fixed design canvas + JS proportional scaling to fit the screen (see the §4 contract).
- CSS / JS fully inlined in `<style>` / `<script>`. CDNs allowed: **Three.js r128**, GSAP, ECharts, D3, Google Fonts. **External image URLs are forbidden** (images may only come from local files under assets/).
- Workspace files: `plan.md` (your plan), `deck.html`, `assets/` (optional), `shots/` (render screenshot output).

## 2. Workflow (six phases)

**Render before you inspect: reading code alone does not count as self-checking.** Rendering always runs the skill's bundled script via bash:

```bash
python skills/dazzle-deck-en/scripts/render_deck.py deck.html shots/ --page N   # render page N
python skills/dazzle-deck-en/scripts/render_deck.py deck.html shots/ --all     # all pages + contact_sheet.png
```

On success, stdout prints one PNG path per line (warnings prefixed `[console]/[static]/[blank]/[nav]` are printed before the paths); render metadata is written to `shots/render.json` (console_errors / static_pages / blank_pages / page count / navigation mode). After screenshotting, inspect with `vision_analyze`.

### Phase 0 — Understand the query and set the tone

The query is usually only a sentence or two; page count, language, audience, and style are mostly yours to decide:

- Page count: follow the query if given; otherwise pick **8–12 pages** based on content volume.
- Language: follow the query's language; keep each page's language naturally uniform.
- **First judge the formality of the usage scenario** (§3 scenario fit), and use it to bound the style candidate domain and the animation density tier.
- **The style must be named explicitly**: `read_file skills/dazzle-deck-en/references/style-families.md` (**continue reading per the §0 iron rule until no longer truncated, not just one read**), and pick one family that fits both the topic and the scenario (if the query carries a style preference, land on a concrete family within that direction).
- `read_file skills/dazzle-deck-en/references/fancy-cookbook.md` (**continue reading per the §0 iron rule until no longer truncated; read the complete technique recipe reference**), and pick 2–3 technique recipes for this deck (one global background, one entrance choreography, transitions / easter eggs as needed).
- **Define one "signature visual"**: every deck needs one signature move worthy of its subject. **Choose the technique that fits the subject best — CSS/SVG/Canvas-2D/shader/code-built 3D are equals; creative and subject-bound = full-score fancy** (pure-CSS geometry or a Canvas-2D concept visualization can be stunning too). **fancy ≠ 3D**; the judgment is "has ideas vs. mediocre boilerplate", not whether 3D was used. **Distinguish the two uses of 3D/shader**: ① a **lively background layer** (shader flow field / node sphere / Fresnel glow sphere / particle stream / 3D ambience layer) — the background should be "alive" by default (continuous subtle motion); this kind of background layer **works for any subject, is a particular plus for tech/abstract/data/network topics, and does not count as "forcing 3D"** — use it freely; ② an **immersive roaming scene** (building the entire deck inside a navigable 3D world + page-turn camera moves) — this one is only for subjects with a spatial main body (architecture, celestial bodies, terrain and landforms, etc.; molecular crystals and physical products in 3D also qualify). **Don't make the background a static dead plane just to "avoid 3D". Guard against both collapses**: don't default to "canvas particle background + editorial typography" regardless of subject, and don't default to "immersive roaming + page-turn camera flips" either — both are boilerplate.
- **Fact-gap judgment**: when the content involves external facts you don't reliably know (real data, recent events, specifics of real people/products/organizations and their timelines) and web_search is in the tool list, verify and fill the gaps per §6b before writing plan.md; knowledge you already reliably hold needs no searching.

### Phase 1 — Write plan.md

Write out the complete plan in a single write_file, including:

1. **Scenario judgment**: what scenario this deck serves, the formality tier (formal / free / subject-led), the animation density tier, and why this family — spell out the reasoning for the fit.
2. **Design system**: family name; precise palette (hex for `--bg / --ink / --accent / --accent-2`); display + body fonts (including a Chinese font fallback); global background layer approach (**CSS/Canvas-2D procedural texture / particle flow field / shader noise / code-built 3D scene / multiple scenes per page — pick one according to the signature visual**, don't reflexively default to any one); shared transition approach.

2b. **Signature visual (one mandatory line)**: this deck's signature move + why it fits the subject/scenario; if you chose 3D/immersive/shader, state what you will build it with. **Once declared it must actually be delivered** (see §5 signature delivery).
3. **Page order table**: one line per page `NN | page type | one-sentence content | this page's fancy technique | layout skeleton`. Page types from: cover / agenda / viewpoint / data / comparison / process / case study / architecture / timeline / summary; adjacent pages must not repeat the same page type; no fancy technique should recur on more than 2 pages. **The "layout skeleton" column must think through how this page is zoned, where the main visual sits, and who owns the leftover space** (e.g. "narrative left, large image right / centered single hero / four equal cards in a row / full-bleed scene / title on top, two-column comparison below") — any number of zones is allowed, but unjustified whitespace is forbidden (see §7 layout and whitespace); pre-plan how parallel items get equal-height alignment. Think the layout through in the plan and the first draft needs less rework. **When using "3D roaming scene + page-turn camera moves", every page must additionally mark `camera anchor=<this page's subject>` in the "fancy technique" column** (e.g. `camera anchor=the Sun`, `camera anchor=main hall · dougong brackets`), pinning down "which page's camera aims at which subject" at planning time for page-by-page self-checks; adjacent pages should aim at different subjects where possible — don't anchor every page to the same one (otherwise the camera effectively never moves).
4. **Asset list** (if needed): judge "photographic necessity" page by page (§6); for those needed, draft the image-generation prompt and its purpose. **Decide per whole group for parallel same-kind objects (N cards / a row of the same category)**: list all N members and choose "all real images" or "all code-drawn" for the entire group — if real images, list one line per member; never let the page table say 4 cards while the asset list holds only 2 images (see §6).
5. **Facts and sources** (only when §6b web research was done): list line by line `fact | source URL`. During page-by-page filling, cite the verified facts recorded here rather than restating from memory.

Plan self-check: is the palette in precise hex? Did it slide back to a warm beige/cream base? Do page types vary? Is the content genuinely credible (real subjects, real data, not placeholder words)? Are the external facts you used backed by sources (§6b)?

### Phase 2 — Generate assets (only when real images are truly needed)

Generate images per the discipline of §6: generate → verify with `vision_analyze` (content correct? palette matching? any text watermark?) → if unqualified, revise the prompt and regenerate; **never force-use a bad image**; record the exact paths into plan.md. Decks without photographic necessity skip this phase (most decks should).

### Phase 3 — Write the global skeleton shell (skeleton only, no page content)

Write a **complete, runnable but page-empty** `deck.html` skeleton in one write_file (structure contract in §4):

- head (Google Fonts / CDN) → `:root` design tokens → all base CSS (.deck/.slide/.active/nav UI/shared keyframes library/shared transition) → `#bg-layer` global dynamic background (**fully implemented and running**, not a placeholder) → N empty `<section class="slide">` (each containing only a `<!-- SLIDE NN: page type + one sentence -->` comment, **no real content whatsoever**; sole exception: the cover section may hold **one line of plain-text main title** — no layout structure, no page-local styles, no entrance animation, no `slideInits[1]` registration; its only purpose is to give the smoke render something visible) → navigation controller JS → page number + progress bar.

**Hard discipline: skeleton = structure, not content. One-sentence criterion: in this write_file, the only thing allowed inside any `<section>` besides comments is that single plain-text cover title.** Do not finish any page during the skeleton phase, let alone dump multiple pages of content at once — that would land a whole batch of pages never verified page-by-page, accumulate cross-page errors that get harder to clean up later, and throw away the entire value of per-page "render as you go" verification.

**Red Flags — if any of these thoughts arises during the skeleton phase, stop and strip the content back to comments before continuing:**

- "The cover is about to be written anyway; finishing page 1 inside the skeleton is more efficient" → violation. The cover too must go through Phase 4's fill→render→inspect loop; during the skeleton phase keep only that one title line.
- "Let me scaffold some page's heading hierarchy / card frames / decorative elements first to save effort later" → violation; that is content filling.
- The skeleton write_file contains any page's body copy, `#sNN` page-local styles, or `slideInits[N]` registrations → violation; delete down to comments only.

Then smoke-verify: `render --page 1` + inspect the image — cover visible, page number/progress bar present, background layer moving (check stdout's [static] and [console]), zero errors. If the skeleton fails, fix the skeleton first, then move to page-by-page filling.

### Phase 4 — Fill page by page (one loop per page, no skipping)

Follow the page order **starting from page 1 (the cover), one page at a time** — the cover holds only a one-line placeholder title in the skeleton; only now is it replaced with full content, going through the same complete mini-loop; there is no such thing as "the cover was already finished in the skeleton phase". Each page completes a full "fill → render → inspect" mini-loop before moving to the next page:

1. `edit` to replace **that one page's** empty section with complete content (page-local styles may live in a `<style>` inside the section or be written into the global style under a `#sNN` prefix; page-local JS must always be registered to `window.slideInits[N]`, see §4). **One edit fills one page only**; do not pour multiple pages of content into a single edit. **When landing this page, build the layout per §7 "vertical leftover must have an owner"** — assign ownership of vertical leftover on content pages right then (no unjustified inter-element whitespace, no bottom content clinging to the footer, and similar adhesion problems); don't defer collapsed bottoms or one-sided dead white to refine time.
2. `render --page N` → `vision_analyze` that page's screenshot, self-check against §5. **Render-then-inspect is a hard requirement** — filling the next page without rendering is not allowed.
3. Hard defects → minimal change → re-render and re-inspect, **at most 3 rounds per page**. Pages that pass are not revisited; move on to the next page.

If filling reveals a fact gap the plan didn't cover and you don't reliably know: verify it per §6b, add the fact + source to plan.md, then land the page — never improvise numbers from vague memory.

Why insist on page-by-page: each page gets individually inspected the moment it lands — confirmed free of overflow/occlusion/errors — so problems are found and fixed when they are cheapest; this is also the core rhythm this skill teaches the model: incremental building + immediate verification, not writing everything at once and gambling that it's right.

### Phase 5 — Global review

`render --all` → first scan **contact_sheet.png** for a one-image global sweep: style drift, adjacent-page sameness, page-number continuity, background consistency across the set; then check render.json: **console_errors must be empty**; for static_pages verify page by page whether each is "static for a reason" (§5). On finding problems: single-page problems → edit that section and inspect only that page's full-size shot; **only cross-page/systemic problems justify changing `:root` tokens or the shared skeleton — but tokens / shared CSS ripple into every page (including earlier pages that passed during page-by-page filling and are no longer revisited), so after the change you must `render --all` and re-scan every page to confirm nothing else got skewed; never sign off by looking only at the original problem page.** Global layout-token adjustments fit best at this step (it already runs render --all). With spare capacity, add page-level exclusive transitions/easter eggs to key pages now.

### Phase 6 — Wrap-up

Before wrap-up, Phase 5's global review must already be done (`render --all` + contact sheet inspected), and **after the final edit there must be another render verification** — wrapping up unverified is not allowed. Then a short text summary: page count, style family, the 1–2 fancy points you're proudest of, and **an honest report of remaining issues** (which page still has what unfixed). **Claiming "all passed" while hard defects remain = the entire deliverable is void.** No "Thanks for listening / Thanks for watching" boilerplate closing pages.

## 3. Scenario fit: the boundary of fancy

**Fancy means maxed-out execution quality and visual impact, not stylistic transgression.** Giving a thesis defense cyberpunk neon and giving a product launch a gray-white template are the same failure. Phase 0 must first settle the scenario's formality:


| Tier      | Typical scenarios                 | Style candidate domain                                 | Animation density                                                                               |
| ------- | -------------------- | ------------------------------------- | ---------------------------------------------------------------------------------- |
| **Formal tier** | academic defense, government/enterprise reporting, medical/financial/legal reports | composed families such as dark business, editorial magazine, data dashboard (**Swiss minimal / International Typographic Style forbidden**) | **Presentation-grade**: restrained deep background micro-motion + refined entrance choreography + data animation (count-up / draw-in); a settled static frame is the norm; neon glitch, particle bombardment, and heavily distracting effects forbidden |
| **Free tier** | product launches, creative pitches, tech shares, personal portfolios | the dazzle cluster unleashed: cyber, immersive 3D, maximalist, Memphis…          | **Show-grade**: cross-page transition effects, particles / 3D / shaders, dramatic choreography at full throttle                                           |
| **Subject tier** | culture & tourism, children's education, arts & culture, food      | follow the subject's temperament (culture → Eastern aesthetics, children → bright illustration…)            | between the two tiers; motion forms fit the subject's metaphor                                                                  |


- Formal-tier focus: typographic tension, data visualization done to the fullest (real data + animated entrances), deep background layering (slow gradient flow, subdued geometric micro-motion, restrained shader noise), clean crisp transitions. **Restraint ≠ low ambition** — a signature memory point is still required, achieved through refinement rather than noise; never neon/glitch/cyber/3D spectacle.
- **The subject tier picks technology by subject**: **subjects with a spatial main body** (architecture, celestial bodies, terrain and landforms, etc.) may have their space built in code as a **3D roaming scene** and "performed" (Forbidden-City-roaming grade); **other subjects** must not force a 3D roaming scene — but **a lively 3D/shader background layer (shader flow field / node sphere / particle stream, etc.) should be used when apt**; the foreground picks the CSS/SVG/Canvas-2D expression that fits the subject best; don't leave the background a static dead plane.
- plan.md must state the tier and the reasoning; scenario words in the query ("defense", "roadshow", "group meeting") are the most important evidence.

## 4. Deck architecture contract (the skeleton must satisfy)

```
<body>
  <div id="bg-layer"></div>            ← global dynamic background layer (canvas/Three.js/CSS animation)
  <div class="stage">                  ← centering container, position:fixed; inset:0; flex centered
    <div class="deck" id="deck">       ← fixed 1280×720 design canvas, overflow:hidden
      <section class="slide active" data-slide="1">…</section>
      <section class="slide" data-slide="2">…</section>
      …
      <div class="hud">page number + progress bar</div>
    </div>
  </div>
</body>
```

1. **design tokens**: all colors / fonts / spacing / type-size ladder defined in `:root`, referenced throughout via `var()` only; no scattered bare hex / bare numeric values.
  - Colors & fonts: `--bg/--ink/--accent/--accent-2/--font-display/--font-body`.
  - **Layout tokens (set at skeleton time, shared by all pages → change one place and every page updates; this is the foundation of "fix the root cause, not per-page whack-a-mole")**: safe margins `--safe-x/--safe-y` (e.g. 64/56px; content never crosses these margins, HUD/page number may hug the edge); a systematic spacing scale `--gap-s/-m/-l` (e.g. 12/24/48; inter-element whitespace only comes from this set — no ad-hoc values, so whitespace keeps rhythm); a minimum readable font size `--fs-min` (about 20–22px; body text/captions never shrink below it to cram content — split pages / cut content instead). Giant type uses `clamp(min, Nvw, max)` to balance drama with an upper bound and prevent overflow. **These layout tokens must be pinned down at skeleton time and kept stable**; page-by-page filling works within their constraints; if a token must change midway, it ripples into every page (including earlier passed pages) and requires global re-verification per §5's fix discipline.
2. **Fixed canvas + proportional scaling** (the root cure for overflow/cropping/aspect distortion): `.deck{position:relative;width:1280px;height:720px;overflow:hidden}`; lay out content and set font sizes in px against 1280×720; JS `fitDeck()` scales the deck by `Math.min(innerWidth/1280, innerHeight/720)`, listening to resize. **Never mix units** (the worst case: deck sized in vh while fonts are sized in vw — on letterboxed screens the type blows the canvas apart).
3. **Only one page shown at a time**: `.slide{position:absolute;inset:0;opacity:0;visibility:hidden;pointer-events:none}`, with `.slide.active` flipping all three on. **Non-current pages must be completely invisible** (toggling only opacity without visibility causes pages to bleed through each other); at any moment exactly one page is active; when adding custom styles to an individual page **never change position** (leaving the stacking flow collapses that page to 0 height and blacks out canvases).
4. **Navigation controller** (written in full at skeleton time):
  - Keyboard ArrowRight/Left, Space, PageDown/Up paging; `window.addEventListener('load', () => window.focus())` to grab focus (the prerequisite for keyboard use inside an iframe).
  - On page turn, move `.active` to the target page (the render script identifies the current page by the `.active` class — a hard contract), update the page number and progress bar, invoke `window.slideInits[N]` on the target page (see item 6), and dispatch a `slidechange` event.
  - **URL-parameter direct jump is mandatory**: `new URLSearchParams(location.search).get('slide')` → jump straight to page N (1-based) at initialization. The render script relies on it for O(1) single-page rendering; missing it slows self-checks significantly and triggers a stderr warning.
5. **Global background layer**: `#bg-layer{position:fixed;inset:0;z-index:0;pointer-events:none}`, deck container `z-index:1`. The background animation is **fully implemented at skeleton time**; during review only parameters may be tuned (color/density/speed) — no rewrites. Event listeners attach to `window` (the background layer is non-interactive); sizing uses `window.innerWidth/Height` + a resize listener.

5b. **Background-foreground legibility (mandatory for full-screen 3D / heavy dynamic backgrounds)**: **don't rescue body text by globally dimming the background** — that kills the 3D on covers/section pages too. Instead:

- **Grade by page type**: covers/section pages let the background loose; content/data pages make it locally recede — reduce that page's particles/highlights (dust `opacity→~.25`, weaker glow), and don't let the camera place the 3D subject in the same quadrant as the foreground diagram.
- **Foreground diagrams carry their own backing** (pages with SVG diagrams / canvas / dense small text / data tables): first choice is a **soft-edged radial scrim** — `radial-gradient(70% 70% at 50% 50%, rgba(<bg>,.85), rgba(<bg>,.55) 60%, transparent)` (same hue as `--bg`), holding the center, fading at the edges, 3D still showing through around, no hard frame; dense pages use a **card + `backdrop-filter:blur(6px)`**. **Never hang a bare `<svg><g stroke>` directly on `.slide`** (the background bleeds through the stroke gaps and swallows the text; see fancy-cookbook "background-foreground separation scrim").
- Strokes `stroke-opacity ≥ .5`, line width ≥ 1.2px; pale text/thin lines only where a scrim already exists.

1. **Per-slide JS lazy registration**: page scripts are always written as `window.slideInits = window.slideInits || {}; slideInits[N] = () => {…}`, invoked by the navigation controller when the page activates (with idempotency guards once initialized). **Top-level immediately-executing code must never touch other pages' (or still-unfilled empty sections') DOM** — this is the key to error-free rendering at the empty-skeleton stage and to pages not trampling each other during filling.
  - **The top of the skeleton's `<head>` (before any in-page `<script>`) must pre-place the line `window.slideInits = window.slideInits || {};`** — guaranteeing it already exists whenever any in-page script runs, which eradicates the timing pit "in-page script runs before the main controller → `Cannot set properties of undefined`"; and `goto()`/`?slide=N` direct jump must only be invoked after all `slideInits[N]` registrations.
2. **Entrance animation contract** (the official resolution of "animation vs. screenshot self-check"): each page's entrance choreography totals **≤2s**, all entrance animations must use `animation-fill-mode: forwards` (or both), and **final state = full content** (the render script screenshots at ~2.6s; what it captures is the final state). Persistent animations (background particles, breathing glow, HUD ticker) are exempt from the 2s cap. Never freeze in a boot/loading/unfinished-typewriter state.
3. **The shared transition** belongs to the navigation controller and is written at skeleton time: class-driven (`.slide.leaving` / `.slide.active` + transition/keyframes), defaulting to a choreography with drama (translation + opacity + blur/clip combos, with cubic-bezier easing). Page-level exclusive transitions (particle reconstruction, shader wipes, etc.) are optional review-phase enhancements.
4. **Performance budget**: animate only transform / opacity / filter (never layout properties); keep canvas particle totals and Three.js draw calls restrained (see §8's particle parameter table); persistent animations use requestAnimationFrame and need not pause while the page is hidden (the render check depends on visible motion).

## 5. Render self-check checklist

After each `render --page N` + `vision_analyze`, check against:

**Mandatory — every page must get these right; the bar is "worthy of fancy as the top goal", not "passable, so stop". Items 1–15 below are "can't read / can't understand / badly laid out" hard problems — clear them to zero first:**

1. Overflow / cropping — content crosses the 1280×720 canvas or a container edge; giant type cut in half; text bursting a fixed small box. `overflow:hidden` **crops silently without showing a white edge** — don't assume no bleed means no problem; actively verify the footer/page number/first & last body lines/chart axis labels aren't cut off.
2. Occlusion — decorative elements / big numbers / overlays pressing on body text; **decoration lines, glows, connectors inside SVG/Canvas drawn on top of text** (a draw-order problem: draw text last, or give it an outline/backing plate; see §7 item 6); negative letter-spacing gluing glyphs together (large Chinese headlines especially).
3. Placeholder residue / empty shells — empty chart containers, KPIs all 0, tables with only headers and no data rows, axes with no curves.
4. Broken images/charts — img / canvas / Three.js / ECharts not actually rendered (black blocks, blank regions).
5. Chinese tofu blocks — font not loaded (Chinese must be imported via Google Fonts and placed in the font-family chain of every element that displays Chinese).
6. Insufficient contrast — text unreadable against its background **or against the illustration / lines / gradients it sits on**; dark styles must stay readable too.
7. Palette breakout — colors outside the palette creeping in (ECharts defaults, generated images running off-color and left unharmonized).
8. **console error ≠ 0** — check stdout's `[console]` lines and render.json; a JS error usually means all subsequent animation/paging is dead.
9. Entrance animation not at final state — text half-transparent / mid-translation in the screenshot (meaning the animation exceeds 2s or lacks fill-mode: forwards).
10. **Grid-texture backgrounds** — graph paper / blueprint grid / perspective grid floor (horizon grid) / regular dot matrix / Three.js GridHelper as background: **all count as hard defects, delete them** (see §7 item 10).
11. **Bare foreground on a dynamic background** — a content page with SVG diagrams / dense annotation text / data tables whose foreground has no scrim soft backing or `backdrop-filter` card and floats directly on a 3D / particle background, making body text or diagrams hard to read — **a hard defect**. Fix per §4 item 5b: give the foreground a soft-edged radial scrim or a card backing + reduce that page's background density; **do not globally dim the background**.
12. **Mixed image sources within a group** — in a group of parallel same-kind objects (a set of dishes / local products / exhibits / people…) some members use real generated images and others use SVG code drawings, fracturing the image-text style — **a hard defect** (see §6: unify the whole group; generate the missing ones or switch the whole group to code).
13. **Collapsed bottom / one-sided dead white** — content occupies only the upper half; the bottom or one column shows a large blank **with no articulable reason** (parallel columns not bottom-aligned, flex children crowding the top, content's natural height not reaching the safe-area bottom edge; this is the most often waved-through, most typical AI sloppiness). **Hard test on the image**: imagine the safe-area bottom edge as a line — does the main content area extend near it? Are parallel columns / card rows bottom-aligned? **The criterion is "is there a compositional reason"**: centered and vertically balanced → legitimate, pass; **an unjustifiable collapsed bottom / edge white / bottom content glued to the footer → hard defect**; fix per §7 "vertical leftover must have an owner + fill scaffold" (container `flex:1` to fill + `justify-content` to distribute / equal heights / centering) — do not leave it. (Note: this rule means "give leftover a reason", not "fill every pixel" — don't stuff deliberately airy / centered pages just to pass the check.)
14. **Orphan last lines / unbalanced breaks** — a multi-line text block whose last line holds only 1–3 characters (centered long subtitles / pull quotes fail most often), **a hard defect**. Hard test on the image: check the last-line length of every multi-line text block. Fix per §7 line-break hygiene: add `text-wrap:balance` / narrow the `max-width` / tweak the wording until line lengths balance.
15. **Anchor misalignment** — markers that should land on a graphic don't: timeline nodes off the curve, connector endpoints not reaching nodes, callout leaders not pointing at their targets, chart markers hovering beside the data points — **a hard defect**. Hard test on the image: trace the curve / connector with your eyes and verify every should-be-on-line point one by one. Fix per §7 same-source anchoring: produce markers and graphics from the same coordinate system, not pixel-nudging and hoping.
16. **3D camera off-target** (check only for decks using "3D roaming scene + page-turn camera moves") — the camera moves on page turn, but **what it aims at is not the subject this page's copy is discussing**: the page about the Sun has the camera drifting elsewhere; a page about some building looks at empty ground; two subjects each half-set so the camera lands in the gap between them; or a subject listed in the plan never enters the frame — **all hard defects** (this is exactly the symptom of "the background spinning aimlessly with page turns, unrelated to content"). Hard test on the image: for each page ask "is the 3D subject at frame center / as the main visual the very thing this page's copy is discussing?" For pages about a local detail also ask "has the camera pushed in close to that subject — can the detail be seen clearly?" Fix: change the rig's `look` to **reference the current page subject anchor's `.position`** (§8 item 8 + fancy-cookbook "camera waypoint moves"), not nudging numbers and hoping — the same principle as #15 same-source anchoring, generalized from "2D markers landing on lines" to "3D camera landing on subjects".

**Signature delivery (hard discipline)**: the signature visual declared in plan.md item 2b must be **genuinely implemented** in the deck. **Downgrading it into filler is strictly forbidden** — if you declared "code 3D scene / immersive_3d / immersive", the deck must truly contain a Three.js 3D scene (geometry + lighting + camera motion); faking "immersion" with 2D canvas particles is a fail; either build it up into real 3D, or honestly amend the plan to the mode you actually built (no false reporting). **When 3D is the signature, the self-check must verify "is the 3D subject itself recognizable as what it is"** (not just the 2D overlay) — a dark base + fog easily smears the 3D subject into a black blob with the content carried entirely by the 2D layer; that is a signature in name only; if it's murky, add rim light / brighten / reduce fog / change the camera position.

**[static] is a signal, not a hard defect**: `[static] page N` on stdout means the page showed no visible motion within the sampling window. Ask yourself: is this a **conscious design** (a data-dense formal-tier page, a quiet page for pacing), or laziness? Static with a reason → ignore and continue; can't state a reason → add motion appropriate to this page's density tier (background micro-motion / data animation), **not mindless particle piling**.

**Layout hygiene (equally mandatory — don't skip it as a "soft defect")**: whitespace, alignment, hierarchy, and letter-spacing must be fixed as thoroughly as the overflow/occlusion above —

- **Whitespace imbalance**: promoted to **hard defect #13 (collapsed bottom / one-sided dead white)** — **unjustifiable** dead white (content pinned to the top / hollow bottom / sawtooth white from unequal parallel columns) is same-tier mandatory as overflow and occlusion; fix per §7 "vertical leftover must have an owner"; don't skip it as soft.
- **Misalignment**: same-page elements not aligned to a common grid / baseline; mixing centered and left-aligned.
- **Muddled hierarchy**: no primary/secondary visual weight; what should pop out doesn't.
- **Letter-spacing**: negative tracking gluing large Chinese headlines, or all-caps small labels that should be tracked out but aren't.

**Only purely subjective marginal polish (a touch more breathing room would feel nicer here, an easing could be a bit smoother) counts as "polish if capacity remains".** Skipping layout hygiene as a soft defect is precisely the main reason decks look "AI-sloppy" — it matters as much as legibility.

**Deck-level self-assessment (at global review)**:

- **Signature-visual ambition**: is the signature worthy of the subject, or mediocre boilerplate? **Both boilerplates count as failing**: mindless "particle background + editorial typography", or subject-blind "immersive roaming + camera flips". Creative 2D/CSS = full marks; the key is technology chosen to fit the topic. **Also check whether the background is "alive"** — degrading into a pure static gradient loses points (unless the foreground carries persistent motion, e.g. maximalist collage); a lively 3D/shader background layer suits any subject; don't hold back just because the topic is "non-spatial".
- The set has at least **2–3 highlight, memorable pages** (a dramatic cover, a stunning data page, an unexpected transition…); quiet pages are allowed to create pacing — **every page a climax = no climax**; style / palette / fonts consistent across the set with no drift.

**Fix discipline**: at most 3 rounds of edit→render→inspect per page, each round making only the minimal change that removes the problem; **collapsed bottoms / one-sided dead white (hard defect #13) rank with overflow / occlusion — they must be fixed until "leftover has an owner"; "that's all the content there is" is not a pass excuse**; **buying a pass by "deleting the animation / background / effects" is forbidden** — fixing means fixing bugs, not downgrading; if an effect truly must be removed, justify it in the wrap-up summary; after 3 rounds keep the best version and record honestly. **When the same flaw recurs across pages (whitespace / alignment / tracking / spacing systematically off), fix the root cause in `:root` tokens or the shared skeleton — not per-page whack-a-mole edits** — more accurate, and saves rework and context. **But always remember the blast radius of shared tokens / CSS is global: it changes every page (including earlier pages that long since passed and are no longer revisited)**: during Phase 4 page filling, prefer `#sNN` page-local overrides for **local** fixes; don't touch shared tokens over a single page; when it truly is systemic and only tokens will do, **after the change you must `render --all` to re-verify that previously passed pages weren't skewed** (don't sign off by looking only at the current page) — such global changes are best batched into Phase 5's global review (which already runs render --all). The most robust approach is pinning the layout tokens down at Phase 3 skeleton time, so page filling works within fixed constraints and never needs mid-course token changes at all.

## 6. Imagery and image generation (when image_generate is available)

**Default is code drawing.** Charts / data visualizations / abstract concepts / geometric decoration / icons / UI elements **must never be generated as images** — draw these with SVG / Canvas / CSS; that is this skill's signature strength. Image generation is for **scenes that need real photographic imagery**: real physical objects, natural scenery, food, and the like. **Famous artworks and real-person portraits in particular must be generated — imitating them with SVG/CSS code is strictly forbidden** — code-drawing a photorealistic face / masterpiece inevitably distorts and collapses. Whether to use images and how many is your own judgment based on the content's realism needs (don't pad the count, don't dodge out of laziness); the images that are truly needed are generated in one batch in Phase 2.

- **Prompt template** (every image carries the palette and texture words, locking the color family):
`"<subject description>, <composition/angle>, <palette color words> palette, low saturation, editorial photography, <light/mood words>, no text, no watermark"`
where the palette color words come from plan.md's palette (e.g. "deep navy and muted gold"); all images in the same deck reuse the same set of color phrases. Pick the aspect ratio by use (16:9 for full-page backgrounds, 4:3 / 3:4 for half-width figures).
- **Verify after generating**: `vision_analyze` to check whether the content is right, the tones fit the palette, and there is no text/watermark/extra people; off-color → revise the prompt and regenerate; if unrecoverable, apply a CSS color-suppression overlay (duotone / translucent primary-color layer).
- **Harmonize again when embedding**: `filter: saturate(.85) contrast(1.05)` fine-tuning + a gradient mask in `--bg`'s rgba (darker on the text side, lighter on the image side) + a vignette, pulling the image into the deck's gamut; text areas must stay readable.
- **Fancy usage encouraged**: a generated image is not just a flat `<img>` — clip-path irregular crops, mask-image reveal entrances (obeying ≤2s + forwards), mix-blend-mode fusion with the background layer, or use as a Three.js texture. Let real images become part of the visual effects too.
- **Image sourcing must be uniform within a parallel group (hard rule)**: peer same-kind items in a grid / card wall / row on the same page (a set of dishes / local products / exhibits / people / logos / products…) — **either all real images or all code-drawn; mixing within a group is forbidden**. If you decide to generate, generate for every member of the group; if you can't cover all members, the whole group falls back to code — no "`<img>` where we have one, `<svg>` standing in where we don't" (in-group image/code fracture hurts more than an all-code group). Before rendering the group, confirm every member's image is in place; generate whichever is missing or switch the whole group to code. **Self-check**: for each group of N members, either all N real images are present or 0 with the whole group in code; the page table's "N cards" = that group's image line count in the asset list.

(If image_generate is not in the tool list, skip this section; all visuals are code-drawn.)

## 6b. Web research (when web_search / web_fetch are available)

When the content involves external facts you don't reliably know — real data, recent events, specifics of real people/products/organizations and their timelines — verify and fill the gaps with web_search before writing plan.md; knowledge you already reliably hold needs no searching. Discipline:

- **Query specific facts, not broad topics**: aim the query straight at the number/date/name you need to verify, in the language that fact is most likely written in.
- **Stop once you have enough**: stop as soon as the needed fact is in hand; don't re-search the same fact with reworded queries when no new lead has appeared.

- **Results feed text content only**: don't paste page text wholesale (rewrite in your own words for the deck); image URLs found on web pages must never be written into the deck (§1's no-external-image rule stands; real images still go through image_generate only).

## 7. Aesthetic floor (anti AI slop) and the dazzle philosophy

Every deck must have character and a stance; it must never be formulaic AI design:

1. **Fonts**: default Inter / Roboto / Arial / Open Sans / Lato / Space Grotesk / system fonts forbidden; a display + body pairing that fits the theme; don't always reach for retro serifs, don't reuse Fraunces / Cormorant / Playfair over and over. font-family must end with a generic fallback (sans-serif / serif / monospace); numbers / data readouts use a monospace confirmed to contain digit glyphs (JetBrains Mono / IBM Plex Mono, etc.). **Large Chinese headlines must use a font with complete Chinese glyph coverage (Noto Sans SC 800/900, etc.); for punch, stack multiple text-shadow layers / a `-webkit-text-stroke` outline** — English display fonts (Bowlby / Bangers) and most ZCOOL decorative faces have incomplete Chinese character sets; applying them to big headlines yields missing/broken glyphs.

1b. **Rendering safety (characters/icons)**: ① math formulas must not use script glyphs like `𝒩` or combining Unicode (`ε̂`/`ε̃`) — they render as tofu blocks in headless mode; switch to `<sub>/<sup>` or plain ASCII; ② core icons / category symbols use SVG, **not emoji** (emoji fonts are often missing → whole areas go blank).
2. **Palette**: a clear dominant color + a sharp accent, precise hex, non-uniform distribution; no purple-pink gradients on white / generic blue-green gradients / boring grayscale.
3. **Anti-beige**: unless the query explicitly asks for it, warm beige / cream / rice-paper / ivory (#FBF7F0 #F5F1EA #ECE3D0 — warm whites where R>G>B) are forbidden as the main background, as are aged-paper / tea-stain noise / vintage-manuscript base moods. Clean pure darks / cool whites / saturated brand colors are all perfectly fine.
4. **Chinese font coverage**: any Chinese text requires a Chinese font imported via Google Fonts (Noto Sans SC / Noto Serif SC / ZCOOL XiaoWei / Smiley Sans / LXGW WenKai, etc., chosen by style) placed in the font-family chain of every element that displays Chinese; never rely on PingFang SC / Microsoft YaHei alone. Each page's language is naturally uniform; no dual Chinese-English parallel text sets.
5. **Form fit**: a deck is slides, not a web app — no browser-style top bars / side navigation / persistent console shells running through the whole show (LIVE FEED / SESSION / VERSION / pulsing-indicator app-status widgets); metadata goes only in the footer or on the cover.
6. **Content actually drawn out**: charts draw their marks directly from real values; the first screen presents real content; a hero / cover must never be "a giant flat color block with one or two words" — it needs a clear main title + supporting copy + a visual focus. Content needs real subjects and real data (plausible, concrete invented numbers), not placeholder words.

- **Decoration never covers body text**: in the HTML layer use a z-index ladder (background 0 / content 1–10 / overlays 20 / HUD 50); decorative absolute elements get `pointer-events:none` and a z-index below same-zone text. **SVG / Canvas has no internal z-index — only draw order counts: text must be drawn last (above decoration lines, glows, connectors, nodes)**; if text unavoidably sits on graphics / illustration, give it `paint-order:stroke` + a light outline matching the backing color, or bed it on a translucent rounded plate / radial halo, ensuring it reads clearly from any angle (this is the definitive cure for "small labels inside an illustration eaten by the line work").

- **Same-source anchoring (markers must truly land on the graphic)**: for any scenario where "a dot / label / connector endpoint must land on some curve, path, axis, or shape" (timeline nodes, milestone dots on a curve, flow-arrow landing points, chart data callouts, map pins), the marker and the graphic must be **produced in the same coordinate system** — preferably drawn into the same `<svg>`: take the point coordinates from that very path via `getPointAtLength()` (or compute them with the same function that generated the path), then have JS position the text labels from the obtained points; alternatively both the line and the markers are computed by JS from the same data into px and placed together. **Never eyeball-overlay HTML percent-positioned elements onto an SVG curve** — especially since `preserveAspectRatio="none"` stretches the SVG non-uniformly, eyeballed alignment inevitably fails; this kind of misalignment cannot be saved by pixel-by-pixel nudging — once found, switch to same-source production.

1. **Layout and whitespace (whitespace is part of the composition, not leftover scraps after layout)** — not bound to a fixed template; arrange by these criteria, valid for any zone count / any layout:
  - **Draw the safe area first, compose freely within it**: content never crosses `--safe-x/-y` (§4) — the only hard frame; how many zones inside is up to the subject (1-zone hero / 2 columns / 3–4 cards / collage / full-bleed scene all work); don't hard-code an "N zones" template.
  - **Every patch of leftover needs an owner**: whitespace either distributes systematically between elements (spacing only from the `--gap-*` scale, so rhythm stays uniform) or pools intentionally in one place for breathing / emphasis; **leftover must never leak into accidental one-sided or one-corner dead white**. Self-check lens: treat the whitespace as an invisible block — it should have a sense of position and a reason; if you can't state the reason, it's a bug.
  - **Parallel items align to a common baseline / equal heights**: a row of cards / two-column content uses `align-items:stretch` or an equal-height recipe, eliminating the sawtooth dead white made by "one column shorter than the other"; don't leave `flex-start` unaligned.
  - **Content volume drives density**: under-filled → enlarge the main subject / add breathing room / merge pages, **not pinned to the top with a collapsed bottom** (a lone `margin-top:auto` bottom-pin is forbidden; full-height flex columns distribute vertical leftover with `justify-content`); overflowing → split pages or drop to `--fs-min`, not cramming until it spills.
  - **Vertical leftover must have an owner (choose one of three by compositional intent + content volume, not "must fill")**: ① **fill and distribute** (plenty of content / parallel items); ② **center and cluster** with breathing room (little content / pull quote / hero); ③ **deliberate large whitespace** for emphasis (asymmetric composition). **Only an *unjustifiable* collapsed bottom / one-sided dead white / bottom elements glued to the footer is a bug** — centered-balanced or deliberately airy pages are always legitimate. This contract only governs "does the leftover have a reason"; **it does not prescribe zone structure**: columns / cards / hero / collage / full-bleed scenes remain free choices by subject and should vary from page to page; **don't make every page a "full-height flex column + `space-between`"** (rotate distribution modes: stretch / center / space-between / intentional clustering).
  - **The "fill scaffold" — a copy-paste implementation of option ① (not the only template)**: the content page's root container fills the safe area as a vertical flex column `inset:var(--safe-y) var(--safe-x);display:flex;flex-direction:column`; the main content area `flex:1;min-height:0` absorbs the vertical leftover outside title / footer (when the footer is `position:absolute`, give the main area `margin-bottom` to make way); inside the main area distribute again — multi-row / multi-card flex columns use `justify-content:space-between` (switch to `center` when content is scant), parallel columns / cards get equal heights via grid `align-items:stretch` or child `flex:1`; **children crowding the top by default is forbidden**. **Three real crash cases → minimal fixes**: ① `top:60px;left:72px;width:520px` (top-anchored + natural height, bottom collapses hollow) → add `bottom:<safe>` + flex column + `justify-content:space-between`; ② flex children already have `flex:1` yet crowd the top (missing distribution) → add `justify-content:space-between`; ③ content `grid` at natural height + footer `position:absolute;bottom` (the block occupies only the upper half) → root container flex column, `.grid{flex:1}`, children within columns `flex:1` / centered distribution.
  - **A hard floor against overflow**: fixed containers get `overflow:hidden + child min-width:0`, or `fit-content` / allow wrapping, reserving ≥15% headroom; oversized display titles get max-width and are allowed to wrap — propping with `white-space:nowrap` is forbidden; giant type with `line-height<1` computes height by the actual ink box and keeps ≥24px from neighboring blocks.
  - **Line-break hygiene (anti orphan lines)**: titles / subtitles / centered pull quotes and other short multi-line text always get `text-wrap:balance` (fully supported by the rendering Chromium, effective for ≤6 lines, works for Chinese too); paragraph body text may add `text-wrap:pretty`. **Hard criterion: no text block's last line may hold only 1–3 characters** — estimate line width by "character count × font size" as you write; prefer narrowing `max-width` so lines even out, or tweaking the wording, over leaving two orphan characters dangling.
2. **Overlays and cursors**: canvas trail fades use `clearRect` or `destination-out`; low-alpha `fillRect` full-screen layering is strictly forbidden (it accumulates into an opaque mask covering the text); custom cursors get a z-index no higher than body text and `pointer-events:none`.
3. **Unforgettable details**: at least 2–3 details per deck that people remember — a dramatic opening, a distinctive data animation, an unexpected transition or easter egg.
4. **Grid-texture backgrounds forbidden**: graph paper / blueprint grids / perspective grid floors (horizon grids) / regular dot matrices, and Three.js `GridHelper` — **never used as backgrounds**; this is a badly overused AI trope, not even a single low-opacity layer. For depth/texture use instead: gradient glows, shader noise, particle flow fields, radial vignettes. (**Only "visual grids tiled as a background" are banned**; CSS Grid layout, i.e. `display:grid` page arrangement, is unaffected.)
5. **No boilerplate padding**: don't default to "canvas particle background + editorial typography" regardless of subject, nor to "immersive roaming + camera flips" regardless of subject — both are boilerplate. Pick the technology that fits the subject best (see §0 signature visual); creative 2D/CSS scores just as fully; but lively background layers (3D/shader/particle streams) are broadly applicable — don't leave the background a static dead plane.

**The dazzle philosophy — as dazzling as possible, but dazzling where it belongs**: within the density allowed by the scenario tier, max out visual expressiveness — continuously micro-moving backgrounds, parallax / magnetic / perturbation mouse responses, morphing / glowing hovers, backdrop-filter / mix-blend-mode / mask-image / clip-path, preserve-3d spatial depth, particles and procedural textures, staggered reveals, large-type typographic tension (tracking must never glue glyphs together). **Bring the heavy machinery when warranted — don't dodge it for being hard to debug**: **3D/shader lively background layers (broadly applicable, especially tech/abstract/data/network)**, code-built 3D roaming scenes (spatial-subject topics), multi-scene immersion, and maximalist collage are all bonus points; but heavy techniques must **serve the subject**, not dazzle for dazzle's sake — 2D/CSS that expresses the subject thoroughly is equally top-tier fancy. The background should micro-move continuously by default; a pure static gradient loses points. Dazzle ≠ clutter: however dense, keep hierarchy clear, palette opinionated, and everything fitted to the scenario tier.

## 8. Engineering pitfalls (common bugs; run through before writing code)

1. **JS function reference order**: top-level immediately-executing controller code must not directly call yet-unregistered global functions; guard possibly-undefined ones with `if (typeof fn === 'function')` — a first-line ReferenceError kills all subsequent scripts (paging/animation all dead).
2. **Three.js locked to r128**: `https://cdnjs.cloudflare.com/ajax/libs/three.js/r128/three.min.js` (UMD global is most stable); OrbitControls from `three@0.128.0/examples/js/`, not the r150+ paths (deprecated). `ShaderMaterial({vertexColors:true})` auto-injects `attribute vec3 color`; don't declare it again in the vertexShader (redefinition → particles all black).
3. **Canvas / Three.js sizing and DPI**: `renderer.setPixelRatio(devicePixelRatio)`; `setSize(w, h)` without the third argument; take sizes from the parent element's `getBoundingClientRect()` (the canvas itself may initially be 0) and watch with a ResizeObserver.
4. **Particle parameter cheat sheet** (spherical starfield, camera z≈400, AdditiveBlending): dim 3000 particles / sz 0.5–2.5 / projection factor 300 / alpha 1.0 / mask 0.85; medium 7000 / 1.2–4 / 550 / 1.3 / 0.78; bright 12000+ / 2–6 / 700 / 1.8 / 0.4. Principle: covers should stun (transparent background + multicolor + high alpha), content pages should recede into background (translucent mask + cool monochrome).
5. **ECharts colors**: all series colors come from `:root` tokens; the ECharts default palette is forbidden; chart initialization goes inside `slideInits[N]`; containers need definite dimensions.
6. **Keyboard events**: listeners attach to `window`; `window.focus()` on `load` to grab focus (decks are often embedded in iframes for preview).
7. **Idempotency for incremental filling**: `slideInits[N]` carries an "already initialized" guard (repeated activation must not rebuild canvases / rebind listeners).
8. **Code-built 3D scenes** (when immersive 3D is the chosen signature): assemble a real scene from parametric geometry (Box/Plane/Cone/Torus/Sphere combinations) + the Ambient/Directional/Point trio of lights; the whole deck shares one persistent scene, one camera rig per page, and page turns lerp the camera along an arc (the look-at point must interpolate in sync). **★The camera's look-at point must anchor to the real coordinates of "the subject this page's copy is currently discussing"** — register the subjects that will be discussed as named anchors at skeleton time (`ANCHORS.<key>=mesh/Group`); each page rig's `look` **references the anchor's `.position`, never a hand-written set of similar-looking coordinates**; when discussing a local detail of a subject, push the camera toward that anchor (reduce distance / narrow fov) instead of hovering far away in a wide shot. Hand-copied coordinates drift off, or two subjects each get half so the camera jams into the empty gap between them, producing "the background spinning aimlessly with page turns, unrelated to the current content" — the most typical failure of 3D roaming decks; eradicate it with anchor references. Full examples in `fancy-cookbook.md` "Code-built 3D scene" (with `ANCHORS` registration) + "Single 3D world camera waypoint moves" (with `look` referencing anchors). Get the scene and camera built and running at skeleton time; per page only tune the rig and that page's HTML.
  - **★High-fidelity (when the subject needs to "look real" — you judge by subject whether to push it and how far)**: don't stop at basic geometry + `MeshLambert` flat colors (the plastic toy-brick look). **Realism has no universal recipe — metal lives on reflections, jade on transmission, leaves on subsurface scattering, clouds on volume, velvet on anisotropy; every subject's leverage point differs**. The method is not applying some material preset, but first asking "how does this surface respond to light / what surface details does it have / is the light environment right / does the frame read like a photo", then using the **capability mapping table** in `fancy-cookbook.md` "High-fidelity 3D" to translate intentions into the corresponding Three.js capabilities and writing the implementation yourself. Universal groundwork (nearly always on): shadowMap real shadows + ACES tone mapping + reflective materials paired with a PMREM environment. **Post-processing crashes most easily in headless rendering → must be smoke-tested first with a clean console + a try fallback** (r128 post-processing modules must come from unpkg/jsdelivr; cdnjs lacks them). High fidelity is a bonus: serve the subject, don't template it, and don't pile it up into timeouts and errors for show.
9. **Avoid the cover debugging black hole**: you can't see the DOM/console and can only guess from screenshots, so **prefer a large SVG for the cover/hero's main visual**; use Three.js for backgrounds (particles/starfields/the scene templates above); don't improvise unverified custom geometry on the cover (extremely prone to guess-driven long rework chains). **Big hero images use `<img>` + `object-fit` rather than `background-image`** — in headless rendering a large `background-image` often hasn't decoded by screenshot time, leaving the page near-black.
